## Q1. Median of N numbers WITHOUT sorting the list

**Input representation:** `int a[n]`, a plain array.

**Key idea:** the median is just the k-th smallest element, for k = ⌈n/2⌉ (and,
for even n, the average of the (n/2)-th and (n/2+1)-th smallest). Finding the
k-th smallest is the classical **selection problem** and does not require fully
ordering the array.

**Algorithm — median-of-medians (BFPRT) selection:**

1. If the current sub-range has ≤ 5 elements, sort it directly (O(1) work) and
   pick the middle value.
2. Otherwise, split the range into groups of 5, find the median of each group
   (O(1) per group ⇒ O(n) total), then **recursively** find the median of these
   ~n/5 group-medians — call it the pivot.
3. Partition the full range around this pivot (Lomuto-style) — O(n).
4. If the pivot's rank equals k, return it; otherwise recurse into whichever
   side contains the k-th element, adjusting k as needed.

**Why the pivot is guaranteed to be "good":** the median-of-medians is larger
than at least half of the group medians, and each of those groups contributes at
least 3 elements ≥ it (of the 5) — so it is guaranteed to be ≥ roughly 3n/10
elements, and symmetrically ≤ roughly 3n/10 elements. This guarantees the
partition always throws away at least ~30% of the array.

**Worst-case complexity:**
```
T(n) ≤ T(n/5) + T(7n/10) + O(n)
```
Since n/5 + 7n/10 = 9n/10 < n, this recurrence solves (by substitution) to
**T(n) = O(n)** — a true worst-case linear bound, not just expected. Sorting to
get the median would cost O(n log n), so this is strictly better.

Program: `q1_median_no_sort/median_no_sort.c` — implements `median_no_sort()`
using median-of-medians selection, cross-checked against a sort-based median for
a 13-element array (match confirmed) and timed for n = 10,000…160,000, showing
the no-sort version consistently faster than the O(n log n) sort-based version.

## Q2. K'th smallest element WITHOUT sorting the list

**Input representation:** `int a[n]` plus an integer `k` (1-indexed).

**Algorithm — Quickselect (Hoare, 1961):** a divide-and-conquer selection
algorithm closely related to Quicksort, except it recurses into only **one**
side of the partition (the side containing the k-th element), never fully
sorting the array.

```
quickselect(a, lo, hi, k):
  pick a random pivot in [lo, hi]
  partition a[lo..hi] around it → pivot lands at index p
  rank = p - lo + 1
  if k == rank: return a[p]
  if k <  rank: recurse into a[lo .. p-1]
  else:         recurse into a[p+1 .. hi], with k -= rank
```

**Complexity:**
- **Average case:** a random pivot is expected to roughly halve the search
  range each step: `T(n) = T(n/2) + O(n) ⇒ O(n)` expected.
- **Worst case:** an unlucky/adversarial sequence of pivots (always picking the
  current min or max) shrinks the range by only 1 element per step:
  `T(n) = T(n-1) + O(n) ⇒ O(n²)`.
- Using a **random** pivot (as implemented here) makes the O(n²) worst case
  extremely unlikely for any fixed input. A deterministic O(n) **worst-case**
  bound is achievable by using median-of-medians (Q1) as the pivot-selection
  step instead of a random pivot, at the cost of a larger constant factor.
- The array is never fully sorted in either case.

Program: `q2_kth_smallest/kth_smallest.c` — implements `kth_smallest_no_sort()`;
validated for every k = 1..13 on a 13-element test array against a sort-based
baseline (all match), and timed for n = 10,000…160,000, showing quickselect
running roughly an order of magnitude faster than sorting.

## Q3. Quicksort of N random elements stored in a file

**Input representation:** `input.txt`, a text file with N integers (one per
line), generated by the program itself; sorted output is written to
`output.txt`. In memory the numbers are held in a plain `int a[n]` array read
via `fscanf`.

**Algorithm:** classic Quicksort with **random pivot selection** (to avoid
worst-case behavior on already-sorted or adversarial input), using Lomuto
partitioning, and tail-call elimination on the larger partition (recursing only
into the smaller side) to keep the recursion stack at O(log n) even in unlucky
cases.

**Complexity:**
- **Average case: O(n log n)** — a random pivot splits the array roughly in
  half on average: `T(n) = 2T(n/2) + O(n) ⇒ O(n log n)` by the Master Theorem.
- **Worst case: O(n²)** — if every pivot is the min or max (1-vs-(n−1) split):
  `T(n) = T(n-1) + O(n) ⇒ O(n²)`. Randomized pivots make this exponentially
  unlikely.
- **Space:** O(n) for the array itself, O(log n) auxiliary recursion stack
  (in-place partitioning, no auxiliary array).
- File I/O adds an additional O(n) for reading + O(n) for writing.

Program: `q3_quicksort_file/quicksort_file.c` — generates `input.txt`, reads it,
sorts with the above Quicksort, verifies with `is_sorted()`, writes
`output.txt`, and times performance for n = 50,000…400,000 (all runs confirmed
sorted correctly; timings grow consistently with the n log n expectation).

## Q4. Heap Sort of N randomly generated elements stored in a file

**Input representation:** same as Q3 — `input.txt` / `output.txt`, numbers held
in-memory as `int a[n]`, sorted **in place** using an implicit binary max-heap
(no separate heap data structure needed — array indices `2i+1`, `2i+2` give the
children of node `i`).

**Algorithm:**
1. **Build-Max-Heap:** call `sift_down` on every non-leaf node, from the last
   internal node up to the root, converting `a[0..n-1]` into a max-heap in place.
2. **Repeated extraction:** swap the root (current max) with the last element of
   the (shrinking) heap, decrease heap size by 1, and `sift_down` the new root to
   restore the heap property. After n−1 extractions, the array is sorted
   ascending.

**Complexity:**
- **Build-Max-Heap: O(n)** — although a single sift-down costs O(log n) in the
  worst case, most nodes sit near the bottom of the tree and need very little
  work; summing the actual per-node cost over the whole tree
  (Σ over height h of (n / 2^(h+1)) · h) gives the tight bound O(n), not
  O(n log n).
- **Extraction phase: O(n log n)** — n extractions, each followed by an
  O(log n) sift-down.
- **Total: O(n log n)** in the **best, average, and worst case** — unlike
  Quicksort, Heap Sort has **no O(n²) worst case**, because the implicit
  complete binary tree always stays balanced regardless of input order.
- **Space: O(1)** auxiliary — sorts in place; `sift_down` is implemented
  iteratively so there is no extra recursion-stack cost either.
- File I/O adds an additional O(n) for reading + O(n) for writing.

Program: `q4_heapsort_file/heapsort_file.c` — generates `input.txt`, reads it,
sorts in place with Heap Sort, verifies with `is_sorted()`, writes
`output.txt`, and times performance for n = 50,000…400,000 (all runs confirmed
sorted correctly; timings track O(n log n) closely and remain stable/predictable
across runs, unlike Quicksort's variance).

## How to build and run everything

```bash
cd q1_median_no_sort && gcc -O2 median_no_sort.c -o median_no_sort && ./median_no_sort
cd q2_kth_smallest   && gcc -O2 kth_smallest.c   -o kth_smallest   && ./kth_smallest
cd q3_quicksort_file && gcc -O2 quicksort_file.c -o quicksort_file && ./quicksort_file [N]
cd q4_heapsort_file  && gcc -O2 heapsort_file.c  -o heapsort_file  && ./heapsort_file [N]
```
`quicksort_file` and `heapsort_file` accept an optional command-line argument
N (default 20) to control how many random integers are generated into
`input.txt` before sorting.
